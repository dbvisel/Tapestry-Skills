Remake a tapestry's own **card thumbnail** on a live installation from the
command line, via `scripts/manage-tapestry-thumbnail.sh`.

## Two different "thumbnail" concepts - don't confuse them

- **Tapestry thumbnail** (what this skill is about): the single card-preview
  image of the tapestry *as a whole* - the `Tapestry.thumbnail` column
  (`server/prisma/schema.prisma`), shown in dashboards and the "Samples" list.
  One image per tapestry, always retaken wholesale (a fresh screenshot
  replaces whatever's there, unconditionally - there's no "missing" state to
  check for the way frames have).
- **Frame thumbnail** (a different, related-but-separate concept, *not*
  managed by this skill): the small preview image belonging to one object
  ("frame") placed on a tapestry's canvas. See the sibling
  `tapestry-frame-thumbnails` skill for that.

These are easy to conflate because they're generated by the same underlying
job - see "Why this is a separate script" below.

## When to use this skill

- "This tapestry's card/dashboard preview looks stale or wrong"
- Forcing a fresh screenshot after a significant layout change, without
  waiting for the app's own debounced auto-regeneration
- You specifically do NOT want to touch any frame's thumbnail - just the
  tapestry's own preview image

## Why this is a separate script

`generate-tapestry-thumbnails.ts` (the job both this skill and
`tapestry-frame-thumbnails` schedule) always retakes the whole-tapestry
screenshot *first*, then separately screenshots any frames marked
`scheduledThumbnailProcessing`. The frame-thumbnails skill's
`generateThumbnails()` marks frames *and* thereby incidentally refreshes the
tapestry thumbnail too, as a side effect of the shared pipeline.

This script calls `scheduleTapestryThumbnailGeneration()` directly instead -
the same function, minus the "mark some frames for processing" step. With no
frames marked, the job's frame loop has nothing to do, so this touches *only*
the tapestry's own thumbnail. That's the intentional split: one script per
concept, per the guardrail in `tapestry-frame-thumbnails`'s own docs ("if you
want a script whose actual purpose is managing \[the tapestry thumbnail\],
write a separate one").

## Using the script

Run with the repo directory as `REPO_DIR` (defaults to the current directory -
i.e. run it from the repo directory itself, unless you point elsewhere). The
script file can live anywhere, e.g. a dedicated `scripts/` directory one level
below the repo:

```bash
cd my-tapestry-repo/scripts
REPO_DIR=.. ./manage-tapestry-thumbnail.sh            # list everything, then pick one
REPO_DIR=.. ./manage-tapestry-thumbnail.sh <search>   # filter by title / slug / owner email
./manage-tapestry-thumbnail.sh --help                 # show usage
```

It lists matching tapestries in a numbered table - title, owner, slug, current
tapestry-thumbnail status (`none` / `set`), and last-updated date. After you
select one, it shows the current thumbnail value, then prompts to confirm
(**requires typing `yes`**) before scheduling a remake - unlike the
frame-thumbnails skill, there's no "missing" gate; a fresh screenshot always
replaces whatever's there.

Generation happens asynchronously in the `worker` service, without the app's
normal debounce delay (this is a deliberate one-off action, not a reaction to
rapid live edits) - it's usually done within moments. Re-run the script against
the same tapestry to confirm the change.

Overridable via environment variables (defaults shown, matching a production
deployment's `docker-compose-fnf.yml` setup):

```bash
REPO_DIR=.
COMPOSE_FILE=docker-compose-fnf.yml
ENV_FILE=.env
DB_SERVICE=db       DB_USER=tapestries   DB_NAME=tapestries
EXEC_SERVICE=worker
```

Point these at a different compose file/service/database name for other
installs (e.g. upstream's plain `docker-compose.local.yml` with
`db`/`tapestries`/`tapestries` still as defaults, or a differently-named
database). `EXEC_SERVICE` just needs *a* running container with the server
source and access to Postgres + Redis - `worker` and `server` are both built
from the same image and either works; `worker` is the default since it's the
service that will actually process the job.

## How it triggers generation (no API endpoint involved)

There's no HTTP endpoint for this - `scheduleTapestryThumbnailGeneration()` is
only ever called from server-side code. The script calls it directly: it
`docker compose cp`'s the bundled `run-generate-tapestry-thumbnail.ts` into the
`EXEC_SERVICE` container's `/tmp/`, then runs it via
`npx tsx run-generate-tapestry-thumbnail.ts <tapestryId>` with `REPO_DIR=/app`
set in its environment, then removes the copied file. The runner resolves its
own import relative to `REPO_DIR` (the directory containing `server/`) rather
than assuming a fixed location relative to itself, so it behaves the same
wherever it's actually run from - inside the container (`REPO_DIR=/app`, set
by this script) or directly against a host checkout (`REPO_DIR=<repo root>`).
This runs the *exact* function the app calls - nothing is reimplemented in SQL
or bash. (Same approach as the sibling `tapestry-frame-thumbnails` skill.)

## Guardrails

1. **This script is VM/fork-only, not upstream** - like `docker-compose-fnf.yml`
   itself, it's not part of `internetarchive/tapestry-project`; it assumes a
   production-style Docker Compose deployment.
2. **Tapestry thumbnail only, not frame thumbnails** - see the section above.
   Don't extend this script to touch per-frame thumbnails; use
   `tapestry-frame-thumbnails` for that, or write a third script if some new
   combined need shows up.
3. **No "missing" check** - unlike frames, a tapestry always has *some*
   thumbnail state (`none` or `set`), and this always overwrites it
   unconditionally on confirm. There's nothing to skip.
4. **Generation is asynchronous** - the script only *schedules* it; it doesn't
   wait around or poll. Re-run to check the result.
5. **`REPO_DIR` must actually be the repo directory** (where
   `docker-compose-fnf.yml` / `.env` live) - the script's preflight check fails
   fast with a clear message (including the resolved path it tried) if the
   database isn't reachable, rather than doing something confusing.

## Bundled scripts

| File | Purpose |
|---|---|
| `scripts/manage-tapestry-thumbnail.sh` | Interactively list tapestries (optionally filtered) with their tapestry-thumbnail status, and schedule a remake for one, with a confirmation prompt before doing anything. |
| `scripts/run-generate-tapestry-thumbnail.ts` | Standalone entry point copied into the container at run time; imports and calls the app's real `scheduleTapestryThumbnailGeneration()` from `server/src/tasks/utils.ts`. Not meant to be run by hand outside the container. |
