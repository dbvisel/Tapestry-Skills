Inspect and backfill missing **frame** thumbnails on a live installation from
the command line, via `scripts/manage-tapestry-frame-thumbnails.sh`.

## Two different "thumbnail" concepts - don't confuse them

- **Frame thumbnail** (what this skill is about): the small preview image
  belonging to one object ("frame") placed on a tapestry's canvas - an Item
  row in `server/prisma/schema.prisma`, e.g. an image, video, PDF, or webpage
  item. A tapestry can have dozens of these, one per frame.
- **Tapestry thumbnail** (a different, related-but-separate concept, *not*
  managed by this skill): the single card-preview image of the tapestry *as a
  whole* - the `Tapestry.thumbnail` column, shown in dashboards and the
  "Samples" list. There's no dedicated tooling here for that; if you need one,
  write a separate script rather than folding it into this one.

These get muddled easily because they're generated by the same underlying job
(see "Side effect" below) - but they're different data, different failure
modes, and different things to check when something looks wrong.

## When to use this skill

- "Why don't these images have low-res previews?"
- A tapestry imported from a `.zip` export shows full-res images only, no
  fast-loading previews per frame (a known gap for tapestries imported before
  this server's `Generate thumbnails on import` fix landed - see Background)
- Checking which frames in a specific tapestry have/haven't got a frame thumbnail
- Backfilling frame thumbnails for an already-imported tapestry without re-importing it

## Background

Every frame that can have an inherent thumbnail (`image`, `video`, `pdf`,
`webpage` - see `ITEM_TYPES_WITH_INHERENT_THUMBNAIL` in
`server/src/tasks/thumbnail-generators/index.ts`) gets one generated
asynchronously: a primary rendition plus several smaller derived ones
(`Item.thumbnailId` -> `ImageAsset` -> `ImageAssetRendition[]`, `server/prisma/schema.prisma`).
Normal item creation (`server/src/resources/items.ts`) schedules this
automatically. Zip import (`server/src/services/tapestry-import-service.ts`)
does too, via a post-import call to `generateThumbnails()` - but only as of
commit `003243a` ("Generate thumbnails on import"). A tapestry imported before
that fix landed on a given install has frames with no thumbnail at all, and
nothing retroactively fixes that just because the server code was later
updated - the gap has to be backfilled by hand, which is what this script does.

`generateThumbnails()` (`server/src/tasks/utils.ts`) is the same function the
import path calls: it marks the given items `scheduledThumbnailProcessing =
'derive'` and enqueues a `generate-tapestry-thumbnails` job, which the running
`worker` service picks up and processes (Puppeteer screenshots / sharp
resizes, uploaded to S3). It's non-destructive - `'derive'` never touches an
existing frame thumbnail (custom or auto-generated); it only fills in what's
missing.

### Side effect: the tapestry's own thumbnail gets refreshed too

`generate-tapestry-thumbnails.ts` (the job this script schedules)
unconditionally retakes a screenshot of the whole tapestry and updates
`Tapestry.thumbnail` *first*, before touching any individual frame. So running
this script will incidentally refresh the tapestry's own card thumbnail as
well - that's an inherent consequence of the app's shared job pipeline, not a
feature of this script. This skill's dashboard doesn't track or report on
that; it only ever shows per-frame status.

## Using the script

Run with the repo directory as `REPO_DIR` (defaults to the current directory -
i.e. run it from the repo directory itself, unless you point elsewhere). The
script file can live anywhere, e.g. a dedicated `scripts/` directory one level
below the repo:

```bash
cd my-tapestry-repo/scripts
REPO_DIR=.. ./manage-tapestry-frame-thumbnails.sh            # list everything, then pick one
REPO_DIR=.. ./manage-tapestry-frame-thumbnails.sh <search>   # filter by title / slug / owner email
./manage-tapestry-frame-thumbnails.sh --help                 # show usage
```

It lists matching tapestries in a numbered table - title, owner, slug, frame
count, and **frames missing a frame thumbnail** (of the types that can have
one) - so problem tapestries are visible before you even pick one. After you
select one, it shows a **per-tapestry dashboard**: every frame, its type, and
its frame-thumbnail status (`none` / rendition count / `n/a` for frame types
that never get one / currently scheduled), so you can see exactly what's
missing before doing anything.

You're then prompted to schedule frame-thumbnail generation for **every**
frame in that tapestry (harmless to run even when some already have one -
those are left untouched) - **requires typing `yes`** to confirm.

Generation happens asynchronously in the `worker` service after that; re-run
the script against the same tapestry a little later (a handful of images
typically finish within a minute or so; dozens can take longer) to watch the
dashboard fill in.

Overridable via environment variables (defaults shown, matching a production
deployment's `docker-compose-fnf.yml` setup):

```bash
REPO_DIR=.
COMPOSE_FILE=docker-compose-fnf.yml
ENV_FILE=.env
DB_SERVICE=db       DB_USER=tapestries   DB_NAME=tapestries
EXEC_SERVICE=worker
```

Point these at a different compose file/service/database name for other
installs (e.g. upstream's plain `docker-compose.local.yml` with
`db`/`tapestries`/`tapestries` still as defaults, or a differently-named
database). `EXEC_SERVICE` just needs *a* running container with the server
source and access to Postgres + Redis - `worker` and `server` are both built
from the same image and either works; `worker` is the default since it's the
service that will actually process the job.

## How it triggers generation (no API endpoint involved)

There's no HTTP endpoint for this - `generateThumbnails()` is only ever called
from server-side code. The script calls it directly: it `docker compose cp`'s
the bundled `run-generate-frame-thumbnails.ts` into the `EXEC_SERVICE`
container's `/tmp/`, then runs it via
`npx tsx run-generate-frame-thumbnails.ts <tapestryId>` with `REPO_DIR=/app` set
in its environment, then removes the copied file. The runner resolves its own
import to `generateThumbnails()` relative to `REPO_DIR` (the directory
containing `server/`) rather than assuming a fixed location relative to
itself, so it behaves the same wherever it's actually run from - inside the
container (`REPO_DIR=/app`, set by this script) or directly against a host
checkout (`REPO_DIR=<repo root>`). This runs the *exact* function the import
path calls - nothing is reimplemented in SQL or bash.

## Guardrails

1. **This script is VM/fork-only, not upstream** - like `docker-compose-fnf.yml`
   itself, it's not part of `internetarchive/tapestry-project`; it assumes a
   production-style Docker Compose deployment.
2. **Frame thumbnails, not the tapestry's own thumbnail** - see the section
   above. Don't extend this script to manage `Tapestry.thumbnail` directly;
   write a separate one if that's ever needed.
3. **The dashboard's "missing" count only considers thumbnail-capable frame
   types** (`image`, `video`, `pdf`, `webpage`) - `text` and `actionButton`
   frames never get one and aren't counted as missing. If the app's own
   `ITEM_TYPES_WITH_INHERENT_THUMBNAIL` list changes, update the matching list
   near the top of `manage-tapestry-frame-thumbnails.sh` to keep the count accurate.
4. **Generation is asynchronous** - the script only *schedules* it (same as
   the import path does); it doesn't wait around or poll. Re-run to check progress.
5. **`REPO_DIR` must actually be the repo directory** (where
   `docker-compose-fnf.yml` / `.env` live) - the script's preflight check fails
   fast with a clear message (including the resolved path it tried) if the
   database isn't reachable, rather than doing something confusing.

## Bundled scripts

| File | Purpose |
|---|---|
| `scripts/manage-tapestry-frame-thumbnails.sh` | Interactively list tapestries (optionally filtered), show a per-tapestry frame/frame-thumbnail-status dashboard, and schedule frame-thumbnail generation for one, with a confirmation prompt before doing anything. |
| `scripts/run-generate-frame-thumbnails.ts` | Standalone entry point copied into the container at run time; imports and calls the app's real `generateThumbnails()` from `server/src/tasks/utils.ts`. Not meant to be run by hand outside the container. |
